## 2026-10-29 交流重赏(is_dirtgrade)改由赛场确定 —— 不是临场条件

**问题(用户提出)**:「交流重赏可以通过场地识别来触发」。上一节把 `is_dirtgrade` 归进了「临场条件」默认不计,
但这一条其实**能由赛场百分百判定**,不该跟着枠番/人气一起被砍掉。

**语义出处**:游戏里的交流重赏 = **ダートグレード競走(地方競馬場ハンデ重賞)**。JRA 十场不办交流重赏,
海外赛场(隆尚/圣安妮塔公园/德尔马)也不办 —— 只有地方赛场(本仓库数据里是大井/川崎/船桥/盛冈)办。
所以「是否交流重赏」=「赛场是否地方赛场」,开赛前就确定。

**触发代码核对**(解包,模块:技能数据库内容):

| 技能 | condition | 解析结果 |
|---|---|---|
| 交流重赏◎ 202251(速度+60) | `is_dirtgrade==1` | `{dirtGrade: true}` |
| 交流重赏○ 202252(速度+40) | `is_dirtgrade==1` | `{dirtGrade: true}` |
| 交流重赏× 202253(速度−40) | `is_dirtgrade==1` | `{dirtGrade: true}` |
| 交流重赏之鬼 202254(速度+60 力量+60) | `is_dirtgrade==1` | `{dirtGrade: true}` |
| 奔跑的吉祥物(1) 109802211-b1(+80/+80) | `ground_type==2&is_dirtgrade==1` | `{surfaces:['dirt'], dirtGrade:true}` |
| 奔跑的吉祥物(2) 109802211-b2(+60/+60) | `ground_type==2&is_dirtgrade!=1` | `{surfaces:['dirt'], dirtGrade:false}` |

**改动**:
- 数据(赛道):`tools/make-courses.ts` 给 10100~10199(地方赛场)打 `dirtGrade: true`,共 14 条
  (大井 3 / 川崎 3 / 船桥 4 / 盛冈 4,全部为泥地);JRA 十场与海外赛道不带该字段。
- 数据(技能):`is_dirtgrade` 从 `ENV_TOKENS` / `UNDETERMINED_TOKENS` 移出,改走独立分支
  → `restriction.dirtGrade`(==1 → true,!=1 → false);`andRestriction` / `restrictionIsEmpty` /
  `cloneRestriction` / `clauseObj` 同步加字段。
- 引擎:`clauseSatisfied` 加一行 `(course.dirtGrade === true) !== c.dirtGrade → false`(与 `abroad` 同构)。
- UI:`describeClause` 输出「交流重赏(地方赛事)」/「非交流重赏」;`UNDETERMINED_LABEL` 删掉 `is_dirtgrade`。
- 测试:engine 新增 4 例 —— ①限制子句真/假双分支(东京 vs 大井)②`data/courses.json` 自检
  (地方赛场必须 `dirtGrade:true` 且为泥地,中央/海外必须无此字段)③数据驱动:交流重赏◎ 在大井计 +60、
  在中央泥地与草地计 0、海外泥地也不计 ④奔跑的吉祥物(1)/(2)互补:大井 +80/+80、中央泥地 +60/+60。
  engine 132(15 文件)+ analysis 14 全绿。

**影响面**:`restriction.undetermined` 从 28 条降到 22 条;绿技能精度分层计数不变(409/1988/244)。
只在地方赛场生效:东京2400 选 交流重赏◎ 仍是 0 收益(与本轮改动前一致,因为没有误判成常驻),

## 2026-10-29 绿技能「临场条件」默认不计(用户要求:只算场地/跑法能百分百确定的)

**问题(用户提出)**:「有额外要求的绿技能,比如幸运7、擅长外道默认无收益,只计算可以通过场地或者跑法确定可以百分百发动的绿技能」。
当时 幸运7(+40 速耐力)、擅长外道◎(+60 速)在收益表里照常给正收益,但其实开赛前根本不知道能不能发动。

**根因**:`clean-skills` 把 `ENV_TOKENS`(post_number / popularity / random_lot / grade / is_dirtgrade / time …)
一律当「环境前提,视为满足」,只写进备注、不落任何字段 ⇒ 这些绿技能既没过限制、也没降精度,变成**常驻加成**。

**触发代码核对**(解包,模块:技能数据库内容):

| 技能 | condition_1 | 性质 |
|---|---|---|
| 幸运7 / 超级幸运7 | `random_lot==50&post_number==7` | 抽选 + 枠番 |
| 擅长内道◎○× | `post_number<=3` | 枠番 |
| 擅长外道◎○× | `post_number>=6` | 枠番 |
| 七福即生 | `post_number==7` | 枠番 |
| 伏兵◎○ / 胆小鬼 | `popularity>=4` / `popularity==1` | 人气(赔率顺位) |
| 夜间赛◎○× | `time==4` | 比赛时段 |
| 交流重赏◎○× / 交流重赏之鬼 / 奔跑的吉祥物 | `is_dirtgrade==1` | 赛事分级 → **已改由赛场确定**,见上一节 |
| 不擅长一级赛事 | `grade==100` | 赛事等级 |
| 博弈者 / 投机取巧 / 凶悍博弈者 | `popularity>=4&random_lot_shared==60` 等 | 人气 + 抽选 |

这些条件全部由**开赛时的实际情况**(闸位抽签、人气、随机数、赛事等级、时段)决定,
赛道数据与跑法都推不出来 —— 单马模型没有依据说它一定发动。

**改动**:
- 数据:新增 `UNDETERMINED_TOKENS`(≤`ENV_TOKENS`),命中时记 token 原文;对**常时被动(绿技能)** 输出
  `restriction.undetermined: ["post_number>=6", …]`;非被动技能不加(它们按规则取位发动、本身已标 approx)。
  `is_tight_track`(小回り,可由赛场确定)与 `furlong` 明确排除在外。
- 引擎:`clauseSatisfied` / `restrictionSatisfied` 见 `undetermined` 非空即返回 false
  ⇒ `skillApplicable=false`、`passiveBonusOf` 不计、消融收益 0。
- UI:技能列表与收益表用紫色「临场条件」角标(替换原「不生效」措辞),tooltip/条件栏写明
  「临场条件:枠番≥6(默认不计收益)」;收益表的发动位置列显示「需临场条件」;面板说明补一段。
- 测试:restrictions 新增 3 例(临场条件不适用 / 赛道能确定的照常计入 / 顶层 undetermined 与 anyOf 并存)、
  greenskill 新增 1 例(七福即生·幸运7 计 0),并把「绿加成合并」的数值锚从七福即生换成 独行侠◎+身为队伍的一员
  —— 原锚点其实一直在吃「post_number==7 被丢弃」的便宜。engine 128 + analysis 14 全绿。

**影响面**:28 条绿技能,精确/近似/不支持的计数不变(409/1988/244);其余 185 条绿技能照常计入。
东京2400 默认配置实测:同时选 标准距离◎ + 幸运7 + 擅长外道◎ + 七福即生 + 顺时针◎(逆时针赛道)+ 伏兵◎
→ 只有 标准距离◎ 计 +0.11 马身,其余全部「临场条件」/「不生效」且收益 —,Σ 单项 = 实测总收益 = +0.11。

## 2026-10-25 「先走一步！为什么只有一个马身」—— 消融口径补「逐次发动」

**问题(用户提出)**:先走一步！(201662)在收益表里只有一个 `+3.43` 马身,没有像区段随机技能那样给「期望 + 区间」。

**触发代码核对**(`data/raw/skill-data-lua.json`,201662):

```
condition_1 = behind_near_lane_time>=3&accumulatetime>=10
float_ability_time_1 = 30000   → 3.0s(运行期 ×距离/1000)
float_cooldown_time_1 = 300000 → 30s(运行期 ×距离/1000)
ability_type_1_1 = 27, float_ability_value_1_1 = 3500 → 目标速度 +0.35
```

- 触发代码里**没有 `*_random`**:`accumulatetime>=10` 是"开赛满 10 秒"这一确定时刻,
  `behind_near_lane_time>=3` 是与邻道马的相对位置(单马模型无法判断,按满足处理并记 approx)。
  ⇒ 位置分布不可枚举,**期望/区间无从抽样**(与 弧线大师 `all_corner_random` 那类不同),只有一个确定值。
- 冷却 30s × 2400/1000 = **实际 72s** ⇒ 同场 **2 次**(10s 与 82s),这正是"×2次"的来源;
  这里用的是用户此前确认过的口径(见 2026-10-24 冷却距离缩放勘误)。

**东京2400 / 默认属性(速度2200 智力1800)实测分解**:

| 口径 | 发动 | 收益 |
|---|---|---|
| 只第 1 次(冷却拉长到只发一次) | 175m / 10.03s | +1.45 马身 |
| 只第 2 次(条件推迟到 82s) | 1570m / 82.1s | +1.71 马身 |
| 整条技能都去掉 | 175m + 1573m | **+3.14 马身** |
| 逐次(只去掉第 i 次) | — | 第1次 +1.43 / 第2次 +1.69(和 +3.12) |

第 2 次更值钱:它落在末脚起点(1600m / 83.4s)前 27m,持续 7.2s 跨过起点 → **存速 +0.42**
(= 0.35 × 智力增幅 1.197,rareEvolved + 智力1800),加速段少爬这 0.42 m/s。

**改动**:引擎新增 `SimOptions.inertFirings`(只去掉第 i 次发动的效果,其余各次照常、仍记入发动史);
消融报 `AblationRow.firingSamples`,收益表对多次发动的技能显示「逐次▼」,点击展开每次的位置/时刻/收益,
并与"整条去掉"对照;时机确定且只发一次的技能在数值上加 tooltip 说明为何没有期望。
测试:engine 124 + analysis 15 全绿(新增 ablate.test.ts 逐次拆分 4 例)。

## 2026-10-25 存速(Spurt Speed Carry-over)核对

**问题(用户提出)**:「进入终盘的时候速度技能持续效果还没消失的话应该是会有存速收益的,你再仔细核对一下」
—— 上一轮结尾我说「+0.1/2s 的小 buff 常常在追上目标速度前就过期,完赛时间完全不变」,这句话说绝对了。

**核对方法**:

1. 读解包 `RaceSolver.applyForces` / `getMaxSpeed`:加速度只取 `baseAccel[phase] + modifiers.accel`,
   **与目标速度的差值无关**;速度上限 = `targetSpeed`,而 `targetSpeed = lastSpurtSpeed + modifiers.targetSpeed`。
   即「速度技能 = 抬上限」,不是「加快加速度」。
2. 与 614tools worker 对照(`Bn` 组目标速度、`Hn` 取加速度、`Un` 积分):同一套「上限 + 固定加速度」模型,无分歧。
3. 社区口径交叉验证(umareference 赛道指南、BWIKI「存速」条):「Speed skills are useless while accelerating,
   **though they can last beyond the acceleration, and if they last into the accel, then your starting point is raised**」。
4. 用无头浏览器 + 引擎逐帧轨迹实测边界行为。

**结论:存速在引擎里是有的,来源就是「进入末脚那一帧的实际速度更高」**(`v` 全程连续,终盘只换目标上限,不重置速度)。
逐帧轨迹(东京 2400 结构示例,中盘 19.4236 → 末脚 23.9864,加速度 0.47):

| 技能 +0.25 / 5s 的发动位置 | 结束时点相对末脚起点 | 末脚起点速度差 | 收益 |
|---|---|---|---|
| 40%(960m) | −12.6s(早已衰减完) | 0.000 | 1.25 马身 |
| 50%(1200m) | −0.4s(衰减中) | +0.143 | 1.95 马身 |
| 55%(1320m) | +5.9s(仍在生效) | **+0.250** | 1.47 马身 |
| 59.5%(1428m) | +11.4s | **+0.250** | 0.98 马身 |
| 60%(1440m,=末脚起点) | +12.0s(起点后才发动) | 0.000 | 0.13 马身 |

- 有存速的行(55%/59.5%)在末脚起点就比基础快 0.25 m/s,这段差值会一直保持到双方都爬到末脚上限
  —— 相当于「额外一个加速段」的收益(0.25 × 9~10s ≈ 2.4m)。
- 起点之前就结束的行没有存速(Δ=0),收益只剩中盘那段持续时间口径。
- **起点之后才发动**的行也没有存速(Δ=0),收益只剩「爬到原上限之后那一小段」;
  `+0.25/5s` 只值 0.13 马身,`+0.25/2s` 直接为 0 —— 这就是「加速段把速度技能吃掉」的确切含义。

**为什么上一轮那句「完全不变」不成立**:那只适用于「在末脚起点之后发动、并在马爬到原上限前结束」的技能;
只要技能**跨过末脚起点**,起步速度就被抬高,收益不为零。

**顺带做的可见化(本次新增)**:

- `SimResult` 增加 `spurtStartMeter` / `spurtStartSec`(末脚起点的位置与时刻,体力不足时按 HP 预算推迟)。
- `AblationRow` 增加 `carryOverSpeed` / `carryOverLeftSec`:存速值 = 「完整模拟 − 只去掉该技能效果」
  在末脚起点位置的瞬时速度差(**精确值**,不另做衰减建模)。
- 收益表新增绿底「存速 +x」角标,悬停显示「进入末脚时起步速度被抬高 +x(还剩/已结束 N 秒)」。
  实测:东京2400 选「俊杰之悠(2)」→「存速 +0.18」、收益 +1.35 马身;
  「圣诞夜的奇迹飞驰！」在东京2400 **没有**存速 —— 它在 1200m 发动、12s 后(≈1450m)就结束,
  而该赛道末脚起点在 1600m,结束于起点前 8.5s,已完全衰减。

**测试**:134 例全绿。新增 `packages/engine/test/spurt-carry.test.ts` 6 例
(起点速度=中盘目标速度、持续到起点则起步速度=+技能值、起点前结束无存速、存速收益 > 值×持续时长口径、
起点后发动被加速吃掉、起点后发动但持续够久有尾段收益)+ `ablate.test.ts` 2 例(carryOverSpeed 上报与收益对比)。
校准双锚未漂移。

## 2026-10-25 消融口径修正:只去掉效果、保留发动(不再让回复技能背大招的收益)

**问题(用户指出)**:用 3 个回复技能开启「圣诞夜的奇迹飞驰！」后,**三个回复技能各自都显示 +1.77 马身**,
但回复技能本身没有马身收益。

**原因**:消融是「从牌组里删掉该技能」的 leave-one-out。删掉任一回复 → 回复数 2 < 3 → 大招不发动,
于是该行的边际收益里包含了「连带失去大招」的 1.77。三个回复各背一次,同一份收益被重复计 3 次,
Σ 单项(5.31)远大于实测总收益(1.77)。

**修正**:消融改为「**只去掉效果、保留发动**」(`SimOptions.inertSkills`):
技能照常判定条件/前提、照常记入发动史(所以别的技能的前提计数不受影响),只是不施加任何效果
(不改速度/体力/属性;绿技能则不并入起跑属性)。这样:
- 回复技能行 = 它们自身的价值(体力不吃紧时就是 +0.00);
- 大招行 = 它自己的 1.77;
- Σ 单项 ≈ 实测总收益。
「从牌组删掉会连带损失什么」另用 `AblationRow.dependentIds` 提示(UI 角标「被依赖 N」,悬停列出依赖它的技能),
只针对「必须已发动」的依赖(`usedSkillBaseIds` / `requiresFirstBlock`);`ownedSkillBaseIds` 是持有即满足,不算。

**实测(东京草2400,界面读数)**:
| 行 | 修正前 | 修正后 |
|---|---|---|
| 圣诞夜的奇迹飞驰！ | +1.77 | +1.77 |
| 弯道恢复○ | +1.77 | **+0.00** |
| 直线恢复 | +1.77 | **+0.00** |
| 圆弧艺术家 | +1.77 | **+0.00** |
| Σ 单项 vs 实测总收益 | 5.31 / 1.77 | **1.77 / 1.77** |

**测试**:126 例全绿(新增 2 例:回复技能自身 0 收益且 Σ≈总收益;-b2 前提链下 b1/b2 各算自身并标「被依赖」)。
校准双锚未漂移。

## 2026-10-25 发动前提(技能发动次数)建模

**问题(用户指出)**:「圣诞夜的奇迹飞驰！」要「触发耐力恢复技能次数≥3」才能发动,但模拟里直接发动。
要求把这类**前置触发条件**全部核实一遍。

**根因**:`activate_count_*` / `is_activate_*` / `is_used_skill_id` 等 token 被归类为「依赖他马的近似条件」
(`APPROX_NAME_RE`),处理方式是**整条丢弃 + 标 approx**。当同一条代码里还有位置类 token(如 `distance_rate>=50`)时,
位置照常解析、前提被静默丢掉 → 技能照常发动。

**审计范围**:全库 198 个技能的触发代码含这类 token,逐条与 BWIKI 技能页「触发条件」中文对照:

| token | 处数 | 真实含义(中文触发条件原文) | 处理 |
|---|---|---|---|
| `is_activate_other_skill_detail` | 159 | 「发动第一段技能」/「已发动第一段技能」 | `requiresFirstBlock`:`-b2` 需 `-b1` 已发动 |
| `is_used_skill_id` | 18 | 「发动技能『冲动』」等具体技能 | `usedSkillBaseIds`(按基础 id,忽略 -b1/-b2) |
| `activate_count_middle` | 11 | 「中盘发动技能次数≥2/3」「中盘发动技能次数为7」「技能发动数量≥3」 | `counters.middle` |
| `activate_count_all` | 13 | 「触发技能数≥7」 | `counters.all` |
| `activate_count_start` | 10 | 「序盘技能发动数量≥3」 | `counters.start` |
| `activate_count_heal` | 9 | 「触发耐力恢复技能次数≥3」 | `counters.heal` |
| `is_activate_any_skill` | 12 | 「发动任意技能」 | `counters.all ≥1` |
| `activate_count_later_half` | 4 | 「比赛后半段发动技能数≥1」 | `counters.laterHalf` |
| `is_activate_heal_skill` | 4 | 「发动耐力回复技能」 | `counters.heal ≥1` |
| `activate_count_end_after` | 1 | 「终盘主动技能发动数量≥3」 | `counters.endAfter` |
| `is_exist_skill_id` | 2 | 「场上持有『同理心』技能」 | `ownedSkillBaseIds`(牌组选了即满足) |
| `activate_count_param_skill` | 1 | 「生效的绿技能数量≥7」 | `counters.green`(只数当前赛道生效的绿技能) |

## 2026-10-25 二次勘误:标准距离 = 400m 倍数(与距离档是两条独立的轴)

**问题(用户纠正)**:上一轮把 `is_basis_distance` 当成「标准距离 = 中距离/长距离」,
映射进了 `distanceTypes`。**这是错的**。游戏内定义:

> 標準距離(根幹距離)= 赛程全长为 **400 米的整数倍** 的赛事。
> 1 = 标准距离;0 = 非标准距离。与「短距离/英里/中距离/长距离」这个距离档**完全无关**。

对照数据可见两条轴互相穿插:

| 距离 | 距离档(distance_type) | 400 倍数? | 标准距离◎ | 非标准距离◎ |
|---|---|---|---|---|
| 1200 | 短距离 | ✅ | 生效 | 不生效 |
| 1600 | 英里 | ✅ | **生效** | 不生效 |
| 1800 | 英里 | ❌ | 不生效 | **生效** |
| 2000 | 中距离 | ✅ | 生效 | 不生效 |
| 2400 | 中距离 | ✅ | 生效 | 不生效 |
| 2500 | 长距离 | ❌ | **不生效** | **生效** |

上一轮的错误实现导致:1600/1200(英里·短距离的 400 倍数)反而**不生效**,

**修正**:
- 数据侧 `is_basis_distance` 不再写进 `distanceTypes`,改为独立布尔 `restriction.basisDistance`
  (true = 400 倍数,false = 非 400 倍数;支持 `!=`)。受影响 12 处 / 6 条常时绿技能
  (标准距离◎○× + 非标准距离◎○×)。
- 引擎 `clauseSatisfied` 判定 `course.distance % 400 === 0`。
- UI 赛道摘要直接显示「标准距离/非标准距离 + 距离」,技能限制文案写「标准距离(400m倍数)」。
- 测试改为按距离选赛道:1600/2400 生效、1800/2500 不生效(四种组合都覆盖)。

**为什么之前会错**:上一轮是「按技能名推测语义」(标准距离像中长距离),没有去读定义。

## 2026-10-25 触发代码严格执行(标准距离类遗漏 + 分支 OR 语义勘误)

**问题(用户指出)**:「标准距离」这种要判断赛道长度的绿技能没有生效;要求排查同类问题,
技能发动条件按触发代码严格执行。

**排查方法**:把 213 条常时绿技能与全库 1906 条解包技能的条件字符串逐 token 统计,
对照 clean-skills 的解析分支,找出**被当成「环境前提视为满足」而当掉的真实条件**。

**发现 3 类问题**:

1. **`is_basis_distance`(12 处)被当环境前提** —— 它就是「标准距离◎/非标准距离◎」的判定。
   ⚠ **本条当时的映射(标准→中/长距离)是错的,已由上方「二次勘误」推翻**:
   正确含义是「赛程全长为 400 米整数倍」,现为独立字段 `basisDistance`。
2. **`base_speed/stamina/power/guts/wiz`(116 处)、`motivation`(19 处)、`is_abroad`(5 处)同样被当掉**。
   这三类在我们的模型里都能判定(面板五维、干劲选择器、赛道是否海外),已全部改为装配限制:
   - `base_*` → `statsAtLeast`(>=,含)/ `statsBelow`(<,不含),取**面板值**(不含绿技能与干劲);
   - `motivation` → `motivations`(1绝不调~5绝好调,支持 ==/>=/<=);
   - `is_abroad` → `abroad`(隆尚/圣安妮塔公园/德尔马 = 海外,tools/make-courses.ts 打 `overseas` 标记)。
   典型效果:「拉普拉斯妖(1)」需要 速度≥1200 且 智力≥1200(+100 速度),「(2)」需要 智力<1200(+80);
   此前两条无条件生效,会同时计入。
3. **分支语义错**:`@` 变体与 `condition_1/condition_2` 是「或」,但输出时被压成一层**并集**。
   当某支不限某字段时,并集会把它当成「受限」:如 100281 一支限 `distance_type==1`、另一支不限,
   被压成「限短距离」,技能在英里/中距离上整场不生效。全库 **777 条有多变体,其中 401 条各支限制字段不同**,
   即约 400 条技能受此影响。
   已改为 **DNF 子句**:每支单独成一条子句,输出 `restriction.anyOf = [子句...]`(任一满足即生效);
   单字段差异的分支化简回扁平结构((A∧X)∨(A∧Y) ≡ A∧(X∨Y)),被支配的子句剔除。
   最终只有 **10 条**真正异构的技能保留 `anyOf`(如「爱的澎湃♡(2)」= 国内草地 or 海外泥地)。

**顺带修正**:同变体内同字段多次出现应按「与」取交集(如 `ground_condition>=2&ground_condition<=3`),
早期实现是累加成并集;`distance_type!=N` 与 `is_basis_distance` 同时出现也做交集。
文本侧「条件限制」由并集改为**只补空缺字段**(触发代码为准),避免把「代码限先行」放大成「先行/差行皆可」。
